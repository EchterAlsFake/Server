# Production operation

The working repositories remain under `/home/asuna/Dokumente`. Production is in
`/srv/server`, `/srv/vplan` and `/srv/mcp`. Each has one systemd service and its own account;
the two applications have
private `.env` and `data/`, and a runtime-only `.venv`. Caddy handles public TLS,
ECH and PROXY protocol from the WireGuard relay; application ports use loopback.

## First startup

Fill `/srv/server/.env` and `/srv/vplan/.env` locally. They are owned by `asuna`,
readable by the corresponding service group, and excluded from updates.
The containing directories are read-only to `asuna`; use an editor that saves
in place, such as `nano`, or `sudoedit`. Do not place actual secrets in Git or chat.
Server's signing key must match the public key expected by existing clients.

After preparation, configuration and data initialization are explicit:

```sh
sudo eaf-deploy server --activate
sudo eaf-deploy vplan --activate
```

Server requires payment credentials for the selected NOWPayments mode, the signing key,
access password, SMTP settings and the local GeoIP database. `NOWPAYMENTS_SANDBOX=true`
is supported for a publicly reachable test deployment and keeps the simulation route enabled;
set it to false only when intentionally accepting real payments. Use `LICENSE_EMAIL_FROM`
for the sender.
VPlan requires the real three API URLs, token, school ID and access answers.
Set its optional school login credentials if automatic login recovery is wanted.

Only after both local health checks pass, install the reviewed
`deploy/managed-sites.caddy` as `/etc/caddy/conf.d/managed-sites.caddy`, validate
the full configuration using Caddy's existing environment file and reload Caddy.
Do not replace `/etc/caddy/Caddyfile`: it contains ECH and the relay trust settings.
The public, unauthenticated MCP endpoint is `https://mcp.echteralsfake.me/mcp`.
Only that path is routed; other paths on the MCP host return 404.

## Updating one application

Review or check out the desired source revision in Dokumente first, then:

```sh
sudo eaf-deploy server
sudo eaf-deploy vplan
sudo eaf-deploy mcp
```

Run only the command for the application you are changing. The command snapshots
tracked and non-ignored source files, including your uncommitted edits. It builds
as `asuna`, downloads current Python dependencies satisfying `pyproject.toml`,
runs tests in a separate environment with matching runtime versions, and builds
the frontend/documentation before stopping production. Python lockfiles are not
used. Node uses `npm ci`. Package installation uses copy mode, avoiding hardlinks
between the deployment and writable uv caches.

At cutover the stopped installation is retained under `/srv/.eaf-backups/`.
Its SQLite database, invoice files, configuration and Python environment form a
consistent rollback point. Data and `.env` are copied into the candidate; migrations
and health checks follow. Failure restores the previous installation automatically.
No provider charges or customer emails are generated by the automated checks.

The installed package list is `/srv/APP/installed-packages.txt`. This is a diagnostic
receipt, not an input to future dependency upgrades. Commands execute through
`.venv/bin/python -m ...`, so moving the tested environment does not depend on the
absolute paths embedded in generated console scripts.

MCP uses the source under `Server/mcp_service` and the public Markdown corpus under
`Server/docs/mcp-docs`; its production copy contains no commercial configuration or data.
It exposes read-only resources plus bounded list, read and search tools, without authentication.

Systemd and Caddy changes need separate review and installation; the update command
does not silently replace system configuration. The helper's source is
`Server/deploy/eaf-deploy`, installed at `/usr/local/sbin/eaf-deploy`.

## Backups and recovery

Pre-update backups are local and root-only. They include purchase data and private
school redaction data, not just code. They are not off-machine disaster recovery.
There is no automatic backup expiration: remove obsolete snapshots promptly,
within seven days, and before applicable school-year/data-retention deadlines.
Keep only the current rollback snapshot where possible. Purge failed candidates
containing copied runtime data on the same schedule. Do not publish these backups.

To restore manually: stop the affected service, move the current `/srv/APP` to a
protected recovery directory, then move the selected matching backup back to
`/srv/APP` and start the service. Restore code, environment and database together;
do not run a database downgrade. Check health before accepting public traffic.
Backup paths are printed after updates. Inspect exact paths before removing any
snapshot. A failed build remains at `/srv/.build-APP`; inspect it and move it aside
before retrying. Build candidates contain no operator `.env` or production data.

## Routine checks

```sh
systemctl status eaf-server eaf-vplan eaf-mcp caddy
journalctl -u eaf-server -u eaf-vplan -u eaf-mcp --since today
curl -fsS -H 'Host: echteralsfake.me' http://127.0.0.1:8000/ping
curl -fsS -H 'Host: vplan.echteralsfake.me' http://127.0.0.1:8001/healthz
curl -fsS http://127.0.0.1:8002/healthz
```

Access logs are disabled. Do not enable debug/request-body logging. The production
services cannot read home directories, modify code, access each other's private
data, or acquire privileges. Do not run app services as `asuna` or root.
VPlan must retain exactly one worker. Its sessions and bans reset on restart.

Refresh the GeoIP database explicitly, then restart Server:

```sh
sudo -u eaf-server env PF_SERVER_DATA_DIR=/srv/server/data /srv/server/.venv/bin/python /srv/server/scripts/update_geoip_database.py --accept-license
sudo systemctl restart eaf-server
```

License acceptance is authorized by the operator. The updater uses the current
UTC month's release. It preserves the previous database if download/validation fails.

Keep Node 24, the shared uv binary and `/usr/local/share/eaf-python` maintained.
Existing environments reference installed Python runtimes; preserve those runtimes
while any deployment or rollback environment still uses them.
